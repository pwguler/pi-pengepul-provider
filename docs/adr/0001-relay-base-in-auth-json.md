# Relay base lives on the credential in auth.json

The provider needs a relay base URL that a user can set once per machine. It lives as a top-level `baseUrl` field on the pengepul credential in `~/.pi/agent/auth.json`, beside the API key. pi ignores the field — only the extension reads it — but `auth.json` is the one file the user already edits for this provider, and it is written by the login flow, which is where a hand-edited field would otherwise go stale. Alternatives were rejected: an env var as the only surface needs shell configuration the user asked to avoid; `models.json` is a second file, and pi does not apply its provider `baseUrl` to extension-supplied models; the credential's `env` map is pi's documented place for provider-scoped values, but it reads as interpolation plumbing rather than configuration.

Consequences: `/login pengepul` must prompt for the URL and write it, since pi replaces the whole credential object on login and a key-only login would silently delete the field. `providers.pengepul.baseUrl` in `models.json` must not be set: with a native provider it rewrites every model's baseUrl to one value, collapsing the Anthropic Messages and OpenAI Chat Completions dialect split.

Amended 2026-09-23: `PENGEPUL_BASE_URL` and `PENGEPUL_API_KEY` are supported as overrides that outrank the credential, so the base resolves environment → credential → loopback and the key resolves environment → credential → unconfigured. The rejection of env above holds for env as the *required* surface, not as an override, so `auth.json` stays the durable one; the rejection of `models.json` is unchanged. The relay's own `~/.pengepul/config.yaml` is no longer read, and neither is a pre-0.3 `<agent-dir>/pengepul-models.json`: `auth.json` is the only file this provider reads.
